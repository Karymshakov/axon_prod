## 1. Критические риски (требующие немедленного действия)

### Утечка паролей (Папка `password_backups/`)
* **Обнаруженная проблема**: В корне репозитория присутствует папка `password_backups/` с файлом [backups_kstu.json](file:///c:/Users/user/Desktop/axon_prod-1/password_backups/backups_kstu.json), содержащим хэши паролей и персональные данные (ФИО) пользователей.
* **Риск**: Высокий риск компрометации учетных данных. Даже если репозиторий является приватным, хранение таких данных в Git-истории нарушает стандарты безопасности (GDPR, PCI-DSS) и создает угрозу утечки при несанкционированном доступе к Git.
* **Инструкция по безопасному удалению**:
  1. Удалить физически папку из рабочей директории (уже выполнено в ходе очистки).
  2. Полностью вырезать файлы из истории Git с помощью `git-filter-repo` (или BFG Repo-Cleaner), так как файлы остаются в истории коммитов:
     ```bash
     pip install git-filter-repo
     git filter-repo --path password_backups/ --invert-paths
     ```
  3. Сделать принудительный пуш во все ветки: `git push origin --force --all`.
  4. Провести смену всех скомпрометированных паролей пользователей.

### Утечка отладочных дампов (Папка `scratch/`)
* **Обнаруженная проблема**: Папка `scratch/` содержит временные файлы, SQL-дампы структуры БД (`database2.sql`) и логи переписок.
* **Риск**: Риск утечки структуры БД и переписок клиентов.
* **Решение**: Добавить всю директорию `scratch/` в глобальный `.gitignore` на уровне проекта (в данный момент в `.gitignore` добавлена только `backend/scratch/`, а корневая `scratch/` отслеживается Git).

### Утечки секретов в Git History
* **Рекомендация**: Проверить репозиторий с помощью инструмента `gitleaks` или `trufflehog` для выявления исторических утечек токенов (например, старых `TELEGRAM_BOT_TOKEN` или `GEMINI_API_KEY`). При обнаружении токенов в истории коммитов — отозвать эти API-ключи и сгенерировать новые.

### Отсутствие верификации Telegram Webhook (`X-Telegram-Bot-Api-Secret-Token`)
* **Обнаруженная проблема**: В [telegram_webhook](file:///c:/Users/user/Desktop/axon_prod-1/backend/apps/leads/telegram_views.py#L770) отсутствует проверка секретного токена Telegram Webhook. Запрос обрабатывается без подтверждения того, что он действительно пришел от серверов Telegram.
* **Риск**: Атака типа Spoofing / Impersonation. Любой злоумышленник, узнавший URL вебхука, может слать фейковые POST-запросы и имитировать сообщения от гостей отеля, заставляя ИИ бронировать номера или раскрывать конфиденциальные данные.
* **Решение**: При регистрации вебхука передавать параметр `secret_token` и сверять его во view:
  ```python
  received_token = request.headers.get('X-Telegram-Bot-Api-Secret-Token')
  if received_token != settings.TELEGRAM_BOT_SECRET_TOKEN:
      return Response('Unauthorized', status=403)
  ```

### Django SECRET_KEY
* **Проблема**: В `settings.py` секретный ключ по умолчанию равен `'django-insecure-change-me-in-production'`. 
* **Риск**: Если в продакшене не установлена переменная окружения `DJANGO_SECRET_KEY`, Django запустится с дефолтным ключом, что делает сессии, JWT-подписи и сбросы паролей уязвимыми к подделке.
* **Решение**: Исключить запуск приложения в продакшене при пустом/дефолтном ключе, выбрасывая `ImproperlyConfigured`.

## 2. Аутентификация и авторизация

### Схема JWT
* Система использует `djangorestframework-simplejwt` для авторизации на базе токенов JWT:
  * `ACCESS_TOKEN_LIFETIME`: 15 минут.
  * `REFRESH_TOKEN_LIFETIME`: 7 дней.
  * `ROTATE_REFRESH_TOKENS`: `True` (ротация включена — при каждом обновлении токена выдается новый refresh-токен).
  * `BLACKLIST_AFTER_ROTATION`: `True` (старые refresh-токены вносятся в черный список).
* **Оценка безопасности**: Конфигурация JWT выполнена в соответствии с лучшими практиками безопасности.

### Multi-tenant изоляция данных отелей
* **Как устроено**: Каждая сущность (лид, стадия, сегмент, FAQ, плейбук) имеет ForeignKey на модель `Organization`. 
* **Энфорсмент**: Защита от межтенантной утечки данных (Cross-Tenant Data Leak) реализована через `OrganizationQuerysetMixin` во вьюсетах. При вызове `get_queryset()` принудительно применяется фильтрация `.filter(organization=org)`.
* **Уязвимость**:
  * Если разработчик создаст новый ViewSet и забудет унаследовать его от `OrganizationQuerysetMixin`, по умолчанию DRF выдаст данные всех организаций.
  * *Рекомендация*: Внедрить глобальное интеграционное тестирование, проверяющее, что под токеном Отеля А невозможно прочитать/создать/изменить запись, принадлежащую Отелю Б.

### Разграничение ролей (RBAC)
* Пользователи имеют роли `Role.ADMIN` (администратор отеля), `Role.SUPPORT` (линейный менеджер) и флаг `is_superadmin` (платформенный суперадмин).
* **Уязвимость**: Сейчас во многих местах нет явных проверок прав `is_staff` / `Role.ADMIN` для изменения настроек интеграций (например, смены API-ключей Telegram/WhatsApp). Любой авторизованный сотрудник отеля (даже с ролью `SUPPORT`) может перезаписать API-токены отеля.
* **Решение**: Добавить кастомный класс разрешений DRF (например, `IsOrgAdmin`) для критических эндпоинтов настроек `/api/integrations/`.

## 3. API и сетевой уровень

### Rate Limiting (Защита от флуда)
* **Проблема**: На эндпоинтах входящих вебхуков от Telegram / Instagram / WhatsApp отсутствует ограничение частоты запросов (Rate Limiting).
* **Риск**: DoS/DDoS атака на бэкенд и разорение баланса LLM API. Злоумышленник может симулировать лавину входящих сообщений (флуд), что приведет к перегрузке БД Django и генерации тысяч платных запросов к OpenAI/Gemini.
* **Решение**: Настроить троттлинг на уровне Nginx (модуль `ngx_http_limit_req_module`) или использовать Django REST Framework throttles (`AnonRateThrottle`, `UserRateThrottle`) специально для эндпоинтов вебхуков.

### CORS
* **Оценка**: Переменная `CORS_ALLOWED_ORIGINS` подгружается из `.env`. Однако на уровне настроек прописаны дефолтные RegExp-регулярки разрешений для любых поддоменов CloudFront. Необходимо убедиться, что CORS-политики в продакшене ограничены только реальным доменом фронтенда.

### Заголовки безопасности в Nginx
* **Проблема**: В текущем файле `nginx.conf` полностью отсутствуют важные заголовки защиты.
* **Решение**: Добавить в конфигурацию сервера Nginx следующие строки:
  ```nginx
  add_header X-Frame-Options "DENY" always;
  add_header X-Content-Type-Options "nosniff" always;
  add_header X-XSS-Protection "1; mode=block" always;
  add_header Referrer-Policy "strict-origin-when-cross-origin" always;
  add_header Content-Security-Policy "default-src 'self' http: https: data: blob: 'unsafe-inline'" always;
  ```

## 4. Инфраструктурные риски

### PostgreSQL
* **Риск**: Доступность порта `5432` / `5433` снаружи. В Docker Compose порт БД не проброшен наружу хоста (отсутствует директива `ports`), что является безопасным решением.
* **SSL**: Необходимо убедиться, что соединение Django с БД PostgreSQL внутри сети Docker или AWS ECS использует SSL-шифрование (`sslmode=require`), особенно если БД будет вынесена на отдельный сервер (например, RDS).

### Redis
* **Риск**: По умолчанию Redis запущен в контейнере без пароля. Если порт `6379` окажется случайно проброшен наружу хоста (или открыт в брандмауэре сервера), злоумышленник получит полный доступ к кэшу, сессиям и очередям Celery.
* **Решение**: Защитить Redis паролем через флаг `--requirepass` в Docker Compose и прописать его в `CELERY_BROKER_URL`.

### Docker: запуск от root
* **Оценка backend**: В `backend/Dockerfile` настроен запуск от несистемного пользователя: `USER appuser`. Это отличная практика.
* **Оценка frontend/nginx**: Контейнер Nginx запускается под дефолтным пользователем (обычно root для привязки к порту 80). Рекомендуется использовать образы `nginxinc/nginx-unprivileged` и биндить порт 8080 (проксируя его на хосте через 80/443).
