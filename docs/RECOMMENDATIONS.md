## 1. Архитектурные улучшения

### Разделение монолита на микросервисы
**Честная оценка:** Сейчас разделение бэкенда на микросервисы **не актуально**.  
Текущий монолит на Django отлично справляется с нагрузкой. Переход на микросервисы усложнит локальную разработку, тестирование, деплой и приведет к накладным расходам на сетевое взаимодействие между сервисами (RPC/gRPC).  
*Когда это станет актуальным:* Только при росте кодовой базы до уровня, когда над проектом начнут параллельно работать более 3–4 независимых продуктовых команд, либо при резком росте RPS (более 5000 запросов в секунду к определенной логике, например, к обработчику сообщений ИИ, который можно будет вынести в отдельный Node.js или FastAPI сервис).

### Введение WebSockets для real-time уведомлений менеджерам
**Рекомендация:** **Да, вводить обязательно.**  
В данный момент менеджеры в CRM видят входящие сообщения с задержкой или вынуждены вручную обновлять страницу/настраивать частый поллинг.  
*Решение:* Использовать `django-channels` совместно с Redis (в качестве Channel Layer) для отправки мгновенных WebSocket-сообщений на фронтенд при получении новых месседжей в вебхуках Telegram/WhatsApp/Instagram. Это позволит мгновенно обновлять чат в панели управления при приходе сообщения.

### Оценка LangGraph для мультиагентного пайплайна
**Оценка:** Текущее использование LangGraph полностью оправдано.  
LangGraph предоставляет гибкий граф состояний (StateGraph), позволяющий описывать сложные циклы диалога, переходы между агентами (Router -> Booking -> Consultant) и хранить промежуточное состояние.  
*Альтернативы:* Переход на CrewAI или Autogen не рекомендуется, так как они ориентированы на непредсказуемое автономное общение агентов между собой, в то время как в CRM нам нужен жесткий детерминированный контроль переходов по шагам бронирования, который LangGraph обеспечивает лучше всего.

## 2. Backend-улучшения

### Рефакторинг моделей, сериализаторов и вьюсетов
* **Модели**: 
  * Вынести логику интеграции (поля конфигураций токенов Telegram, WhatsApp, Instagram) из приложения `leads` в отдельное приложение `integrations`. Это разгрузит модель `Lead` (которая сейчас перегружена вспомогательными полями).
* **Сериализаторы**:
  * Оптимизировать сериализатор `LeadSerializer`, создав плоскую версию для списков (ListLeadSerializer) без тяжелых вложенных связей и детальную версию для карточки лида.
* **Представления (Views)**:
  * Перенести обработку логики из `views.py` и `webhook views` в сервисный слой (Service Layer, паттерн «Толстая модель / Сервис, Тонкий контроллер»). Создать сервис `LeadCommunicationService` для отправки и обработки сообщений.

### Улучшение работы с Celery
* **Идемпотентность**: Вебхуки от Meta и Telegram могут присылать дубликаты сообщений с одинаковыми ID. Внедрить проверку уникальности ID входящих сообщений (транзакционно или через Redis-lock на 10-20 секунд) перед запуском таски генерации ответа ИИ.
* **Ретраи (Retry)**: Использовать встроенные механизмы Celery:
  ```python
  @shared_task(bind=True, autoretry_for=(RequestException, LLMError), retry_backoff=True, max_retries=5)
  def _delayed_instagram_ai_response(self, lead_id, ...):
      ...
  ```
* **Мониторинг**: Подключить **Flower** — дашборд реального времени для мониторинга задач Celery, отслеживания зависших воркеров и количества упавших тасок.

### Кэширование с помощью Redis
* Использовать Redis не только как брокер Celery, но и как кэш для Django (`django.core.cache`).
* **Что кэшировать**: Данные профиля отеля (`HotelProfile`), FAQ (`HotelFAQ`) и плейбуки (`Playbook`). Они редко меняются из админки, но запрашиваются при каждом входящем сообщении гостя для формирования контекста LLM. Кэширование снизит нагрузку на PostgreSQL до нуля по этим таблицам.

### Версионирование API
**Рекомендация:** Начать использовать префикс `/api/v1/`.  
Так как мобильное приложение разрабатывается на React Native/Expo и обновляется на устройствах пользователей асинхронно, любые изменения схемы API на бэкенде могут сломать старые версии приложения на телефонах. Версионирование API позволит плавно переводить пользователей на новые форматы запросов.

## 3. Frontend и Mobile

### State Management
* Текущий стек (React Context для глобального стейта сессии/языка + React Query для серверных данных) **полностью достаточен**. Вводить тяжелые библиотеки вроде Redux Toolkit или MobX нет необходимости, так как в системе нет сложной клиентской бизнес-логики вычислений, не связанной с сервером.

### Code Splitting и Lazy Loading
* Применить `React.lazy()` и `Suspense` для загрузки страниц роутера TanStack. Это позволит разбить единый бандл фронтенда на отдельные чанки (страница авторизации, настройки, чат, аналитика) и снизит время первой загрузки интерфейса (LCP) в браузере.

### Offline-режим для мобильного приложения
* Поскольку отельные менеджеры часто работают в зонах с нестабильным интернетом, мобильное приложение должно уметь:
  1. Кэшировать список активных лидов локально через `AsyncStorage` или `SQLite / WatermelonDB`.
  2. Поддерживать оптимистичное обновление интерфейса (Optimistic Updates) в React Query, отображая отправленное сообщение мгновенно и отправляя его в фоне при восстановлении сети.

## 4. DevOps и мониторинг

### Kubernetes: нужен ли?
**Честный вердикт:** **Нет, не нужен.**  
Для текущего масштаба проекта (до 50-100 отелей-тенантов и нагрузки в пределах 10-50 RPS) Kubernetes принесет избыточную сложность в администрировании, увеличит стоимость инфраструктуры (минимальный отказоустойчивый кластер требует 3 ноды) и потребует выделенного DevOps-инженера на фуллтайм.  
*Альтернатива:* Использовать связку Docker Compose / Docker Swarm на одном или двух VPS совместно с балансировщиком трафика (например, Hetzner LB или Nginx).

### Сравнение CI/CD: GitHub Actions vs GitLab CI
* **GitHub Actions** (текущий): Идеален для старта. Имеет бесплатные лимиты минут, прост в настройке и интегрирован с хостингом кода.
* **GitLab CI**: Удобен при локальном self-hosted развертывании инфраструктуры. Для данного проекта переезд на GitLab CI **не имеет смысла**, так как GitHub Actions полностью решает текущие задачи деплоя и автоматизации сборки.

### Мониторинг
* **Минимальный стек**:
  1. **Sentry**: Для автоматического перехвата ошибок бэкенда (Django, Celery) и фронтенда в реальном времени.
  2. **Flower**: Для мониторинга Celery.
* **В перспективе**: Связка **Prometheus + Grafana** для сбора метрик системных ресурсов хоста (CPU, RAM, Disk I/O) и метрик БД Postgres.

### Логирование
* Текущий файловый вывод в `django.log` заменить на вывод структурированного JSON в stdout с помощью библиотеки `structlog`. Это позволит в будущем легко подключить агрегаторы логов (Vector / Promtail -> Grafana Loki) без необходимости парсить текстовые строки регулярными выражениями.

## 5. ИИ-пайплайн

### Prompt-менеджмент
* **Текущее состояние**: Промпты лежат в БД в модели `AIConfig` (с дефолтными значениями в коде) и в файлах `cs_agent.md`, `consultant_agent.md` в папке [backend/knowledge_docs/prompts](file:///c:/Users/user/Desktop/axon_prod-1/backend/knowledge_docs/prompts/). Это создает путаницу: непонятно, какая версия промпта приоритетнее.
* **Улучшение**: Сделать промпты полностью версионируемыми. Хранить системные промпты в Git, а в БД держать только специфичные переменные отеля (название, цены, политики).

### Fallback-логика при сбоях LLM
* Внедрить автоматическое переключение (failover) провайдеров. Если основной провайдер (например, Gemini) возвращает ошибку API или превышен лимит запросов (Rate Limit), Celery-задача должна прозрачно переключить запрос на резервный провайдер (например, Groq или OpenAI), используя фабричный метод в `ai_service`.

### Контроль расходов на API (LLM Cost Control)
* **Токеновые лимиты**: Настроить жесткие лимиты на максимальное количество токенов в ответе (`max_tokens=300` для диалогов).
* **Срезание истории**: Не передавать всю историю переписки (которая может достигать сотен сообщений). Ограничивать контекст LLM последними 10-15 сообщениями диалога + кратким саммари предыдущей беседы, автоматически обновляемым в поле `notes` лида.
